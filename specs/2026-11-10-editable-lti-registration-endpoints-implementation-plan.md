This plan turns the specification into ordered tasks. It authorises no
automatic rewrite of any stored registration, no change to the Canvas token,
JWKS or audience defaults, and no change to issuer uniqueness.

## Outcome

The work is complete when:

1. `createLtiPlatform` accepts the four endpoint fields as optional, validates
   every supplied value server side, and fills each omitted field separately
   from the adapter;
2. `updateLtiPlatform` changes the name, client ID and four endpoints of an
   existing registration, never the issuer, and requires `lti-platforms:edit`;
3. `suggestLtiPlatformEndpoints` returns the adapter's defaults for a valid
   issuer and requires `lti-platforms:create`;
4. the Manager role holds `lti-platforms:read` and `lti-platforms:edit` on new
   databases (reference data) and existing ones (one data-only release script,
   which also grants the missing allowlist abilities);
5. the create form shows the four endpoint fields with a "Fill defaults from
   issuer" button, the details page shows an Edit button to holders of
   `lti-platforms:edit`, and `/admin/lti-platforms/$id/edit` saves a complete
   registration;
6. the Canvas adapter suggests `https://sso.*.canvaslms.com/api/lti/authorize_redirect`
   for the three hosted issuers and keeps issuer-relative values otherwise;
7. tests cover each row of the spec's propagation table;
8. `docs/13-lti.md`, `docs/11-data-model.md` and `docs/08-lms-integration.md`
   describe the new model, and one changeset covers the four packages.

## Findings From the Code

These were checked while writing the plan. Each one either confirms the spec
or changes a task below.

1. **The `lti-platforms:read` gap is real.** `getLtiPlatform` requires
   `lti-platforms:read` (`commands.ts`). The Manager role in
   `reference-data.ts` lists only `lti-platforms:list` and
   `lti-platforms:create`. `AdminAuth` checks abilities with a plain
   `includes` (`packages/core/src/lib/auth.ts`), with no wildcard. No seed,
   release script or fixture grants `read` elsewhere. A seeded Manager
   therefore gets "not found" on every details page. The new edit route's
   loader calls the same `getLtiPlatform`, so it would fail the same way.
   **Decision:** grant `read` together with `edit`, in both places.
2. **No release script has granted an ability before.** The activity URL
   allowlist added `activity-url-allowlist:list` and `:manage` to the reference
   data only (`2026-09-09-001-migrate-activity-url-allowlist.sql` has no
   `admin_permissions` insert). An existing database's Manager role likely lacks
   those too. This plan's script is the first of its kind. **Decision
   (2026-11-10):** the script also grants the two allowlist abilities, under
   the broader name `grant-manager-abilities`.
3. **PostgreSQL 18 is the supported version** (`docs/04-installation.md`, CI
   and the test docs). The release script uses `uuidv7()`, which the session
   suite's seed already uses.
4. **The form needs a server function for the suggestion command.** The spec
   lists `update.ts` and `update.server.ts` but not a host server function for
   `suggestLtiPlatformEndpoints`. The create and edit forms need one. Add
   `suggest-endpoints.ts` and `suggest-endpoints.server.ts`, shaped like
   `generate-canvas-config.ts`.
5. **An ability refusal is not a non-200 response today.**
   `adminSessionMiddleware` checks the session, not abilities. The core command
   returns `{ ok: false, error: { code: 'ERR_FORBIDDEN' } }`, and every sibling
   form action (`create.server.ts`, the admin-roles `edit.server.ts`) turns that
   into a `status: 'failed'` form state, which the server function returns as
   HTTP 200. The spec's session test ("without `lti-platforms:edit` gets a
   non-200 refusal") therefore can't pass with the sibling pattern unchanged.
   **Decision:** split the test in two. A call with no session must get a
   non-200 response from the gate, which is the `8087512` regression the spec
   wants guarded. A call from a session without `edit` must get a failed form
   state, and the row must stay unchanged in the database. That shows the
   refusal is enforced on the server without changing the form-action
   convention. **Decision (2026-11-10):** converting forbidden results into
   HTTP 403 is out of scope. It will be considered, or rejected, separately.
6. **The JWKS rebind test already exists.**
   `launch-characterisation.test.node.ts:228` ("uses a corrected jwks_uri on the next
   launch, without a restart") covers the launch row of the propagation table.
   No new test is needed, only a reference to it from the plan's checklist.
7. **The new `aud` check belongs in `access-tokens.test.node.ts`, not the
   manager test.** `score-submission/tests/manager.test.ts` stubs the
   access-token manager, so it can't see a signed assertion. Put the
   reconciliation case (only `authorization_server` changes, so expect
   `forgetRegistration` and a replacement client) in `manager.test.ts`. Put
   the signing case (the next token request's assertion carries the new `aud`)
   beside `access-tokens.test.node.ts:86` and `:145`.
8. **`lti_platforms` has no `vid` column**, unlike `admin_roles`. Two
   administrators editing the same registration: the last save wins. The spec
   rules out a schema migration, so this plan accepts that and records it in
   the docs.
9. **The issuer is stored verbatim and matched exactly.** `findPlatformByIssuer`
   compares against the launch's `iss`. An issuer entered as
   `https://canvas.instructure.com/` would be valid under the spec's
   `issuerSchema`, yet no launch would ever match it. Because the issuer can't
   be edited, the mistake couldn't be corrected either. **Decision
   (2026-11-10):** `issuerSchema` rejects an issuer whose raw string ends in
   `/`.
10. **`packages/lms-canvas` has no registration test yet.** Create
    `src/registration.test.node.ts`.
11. **Branch name.** The spec names `feat/editable-lti-registration-endpoints`.
    The work is already on `feat/editable-platform-endpoints`, which holds the
    staged spec. Keep the current branch and correct the spec's Delivery
    section in the docs task.

The phases follow the spec's Delivery order. Each phase leaves the tree
passing `pnpm lint:check`, `pnpm typecheck` and the affected package's tests,

### Phase 1 — Core: Validation, Commands and Abilities

**1.1 Validation schemas** (`packages/core/src/modules/admin/lti-platforms/schemas.ts`)

- [x] Add `issuerSchema`: `z.string().trim().max(255)`, refined to an absolute
  URL with `protocol === 'https:'`, an empty `search` and an empty `hash`.
  Check the raw string for `?` and `#` as well, because `new URL` drops an

- [x] Add `audienceSchema`: trimmed, non-empty, at most 2048 characters, no URL

## Decisions — 2026-11-10

The three questions raised in the first draft of this plan are settled:

1. **Trailing-slash issuers: rejected** by `issuerSchema` (Finding 9, task
   1.1). This tightens the spec's rule, and the spec has been updated to
   match.
2. **Allowlist abilities: granted** by the same release script, renamed
   `grant-manager-abilities` (Finding 2, task 1.5).
3. **Forbidden as HTTP 403: out of scope.** The form-action convention stays,
   and the session test is split as Finding 5 describes. Whether admin
   actions should answer ability refusals with a non-200 status will be
   decided separately.
